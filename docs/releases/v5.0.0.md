# Release v5.0.0 - SRE Alerting and Incident Operations

Release date: 2026-06-01

V5 adds SRE alerting and incident operations to the AWS EKS Platform Golden
Path.

The goal of this release is to move beyond metrics visibility and validate a
practical operational loop: alert rules, Prometheus validation, incident
simulation, recovery, and runbook documentation.

## Highlights

V5 adds:

- Helm-managed `PrometheusRule`
- optional alerting through Helm values
- Platform CI validation for alert rule rendering
- namespace-scoped RBAC for PrometheusRule deployment
- EKS validation with Prometheus Operator
- direct Prometheus query validation
- controlled Incident API outage simulation
- recovery validation
- Incident API alert runbook

## Alerting implementation

Alerting is disabled by default in the Helm chart.

```text
alerting.enabled=false
```

Observability mode enables alerting through:

```text
observability/incident-api-observability-values.yaml
```

This keeps the base deployment independent from Prometheus Operator CRDs.

## Alerts

V5 defines four alerts.

| Alert | Severity | Purpose |
| --- | --- | --- |
| `IncidentAPIDown` | critical | Prometheus cannot scrape the API target |
| `IncidentAPIMetricsMissing` | warning | The application info metric is missing |
| `IncidentAPIHighRestartCount` | warning | The container restarted recently |
| `IncidentAPIHigh5xxRate` | critical | The API is returning HTTP 5xx responses |

## CI improvements

Platform CI now validates PrometheusRule rendering.

The CI checks that:

- no `PrometheusRule` is rendered by default
- observability values render a `PrometheusRule`
- all expected alert names are present
- Helm rendering still uses `fullnameOverride=incident-api`

This keeps alert validation fast and independent from a live EKS cluster.

## Kubernetes authorization update

The GitHub Actions deploy Role was updated to manage:

```text
prometheusrules.monitoring.coreos.com
```

The permission remains scoped to the `incident-api` namespace.

This allows the manual deployment workflow to deploy application alert rules
without granting cluster-admin permissions.

## EKS validation

The platform was recreated temporarily for validation.

The Incident API was deployed through the manual GitHub Actions workflow with:

```text
enable_observability=true
```

The PrometheusRule was created successfully:

```bash
kubectl get prometheusrule -n incident-api
```

The rule was accepted by Prometheus Operator:

```text
prometheus-operator-validated: true
```

## Prometheus validation

Prometheus was accessed with:

```bash
kubectl port-forward -n observability svc/observability-prometheus 9090:9090
```

The following checks were validated:

```promql
ALERTS{alertname=~"IncidentAPI.*"}
```

```promql
up{namespace="incident-api", service="incident-api"}
```

Healthy state after recovery:

```text
up = 1
no firing IncidentAPI alerts
```

## Controlled incident simulation

The Incident API outage path was tested by scaling the deployment to zero.

```bash
kubectl scale deployment incident-api \
  --namespace incident-api \
  --replicas=0
```

The cluster correctly reported no application pods in the namespace.

Recovery was performed by scaling the deployment back to one replica.

```bash
kubectl scale deployment incident-api \
  --namespace incident-api \
  --replicas=1

kubectl rollout status deployment/incident-api \
  --namespace incident-api \
  --timeout=180s
```

The deployment recovered successfully.

## Security and operations impact

V5 improves the platform by adding an operational response layer:

- alert rules are versioned with the application chart
- alert deployment is controlled by Helm values
- alert resources are deployed through namespace-scoped RBAC
- alert validation is included in CI
- operational recovery commands are documented
- incident simulation and recovery were validated on EKS

## Out of scope

V5 does not include:

- Alertmanager notification routing
- Slack integration
- email integration
- Grafana dashboard as code
- on-call escalation policies
- long-term incident storage

These remain future enhancements.

## Final outcome

V5 validates the SRE operational loop for the Incident API:

```text
metrics
-> scrape
-> alert rules
-> Prometheus validation
-> incident simulation
-> recovery
-> runbook
```
