

# Release v4.0.0 - Production-Grade Hardening

Release date: 2026-05-27

V4 hardens the AWS EKS Platform Golden Path after the validated V3 manual
deployment workflow.

The goal of this release is to make the platform more production-like without
changing its core operating model:

- CI runs automatically.
- Cloud deployment remains manual.
- GitHub Actions deploys only to an existing EKS cluster.
- Terraform remains the explicit infrastructure lifecycle tool.
- AWS authentication uses GitHub OIDC with no static AWS keys.
- Kubernetes permissions remain namespace-scoped where possible.

## Highlights

V4 adds four main hardening improvements:

- Helm resource naming hardening
- GitHub Environment deployment approval
- Terraform Plan IAM least-privilege policy
- Kubernetes NetworkPolicy intent

## V4.1 - Helm naming hardening

The Helm chart now supports:

```text
nameOverride
fullnameOverride
```

The manual deployment workflow sets:

```text
fullnameOverride=incident-api
```

This standardizes the rendered Kubernetes resource names:

```text
deployment/incident-api
service/incident-api
servicemonitor/incident-api
```

This replaces the previous generated names:

```text
incident-api-incident-api
```

### Why this matters

Predictable names simplify:

- rollout checks
- smoke tests
- ServiceMonitor validation
- Grafana and Prometheus troubleshooting
- documentation and operator runbooks

## V4.2 - GitHub Environment approval

The deploy workflow already targeted:

```text
environment: dev
```

V4 configures the GitHub Environment `dev` with required reviewers.

The deployment flow is now:

```text
workflow_dispatch
-> GitHub Environment dev
-> required reviewer approval
-> GitHub OIDC role assumption
-> EKS deployment
```

### Why this matters

Human approval happens before the AWS deploy role is assumed.

The workflow remains:

- manual
- auditable
- protected
- keyless through GitHub OIDC

## V4.3 - Terraform Plan IAM hardening

V4 replaces the broad AWS managed policy:

```text
ReadOnlyAccess
```

with a custom read policy for the GitHub Actions Terraform Plan role.

The custom policy covers only the AWS read operations required for Terraform
refresh and planning, including:

- caller identity validation
- selected EC2 and VPC metadata
- EKS metadata
- ECR repository metadata
- project IAM roles and policies
- AWS managed policies used by the EKS module
- backend S3 state and lockfile access through a separate policy

### Real validation fix

During validation, Terraform refresh needed:

```text
ec2:DescribeVpcAttribute
```

This was required to read the VPC attribute:

```text
enableDnsHostnames
```

The custom policy was updated and the Terraform Plan GitHub Actions workflow
was validated successfully.

### Why this matters

The Terraform Plan workflow is still non-destructive, but it no longer relies
on AWS account-wide read access.

This improves the least-privilege posture of the CI/CD layer.

## V4.4 - Kubernetes NetworkPolicy intent

V4 adds a declarative NetworkPolicy:

```text
kubernetes/networkpolicies/incident-api.yaml
```

The policy defines the intended network boundary for the Incident API.

It allows ingress to the Incident API pods on port `8000` from:

- the `incident-api` namespace
- the `observability` namespace

It also allows DNS egress to `kube-system` on port `53`.

### Important limitation

On EKS, Kubernetes NetworkPolicy enforcement depends on a compatible policy
engine such as Calico, Cilium, or equivalent.

With the default AWS VPC CNI alone, the NetworkPolicy can be accepted by the
Kubernetes API without necessarily enforcing traffic restrictions.

This release defines the intended network security model and keeps it ready
for enforcement when a compatible policy engine is installed.

## CI improvements

Platform CI now validates the NetworkPolicy manifest offline.

The CI checks that the manifest has:

- valid YAML syntax
- `apiVersion`
- `kind`
- `metadata.name`
- `kind: NetworkPolicy`
- `apiVersion: networking.k8s.io/v1`
- `spec.podSelector`
- `spec.policyTypes`

This keeps CI independent from a live EKS cluster while still validating the
structure of the Kubernetes security manifest.

## Security impact

V4 improves the platform security posture by:

- removing broad `ReadOnlyAccess` from the Terraform Plan role
- enforcing a custom read policy for Terraform Plan
- protecting deployment through GitHub Environment approval
- keeping AWS authentication keyless with GitHub OIDC
- keeping deployment permissions namespace-scoped through Kubernetes RBAC
- defining a Kubernetes NetworkPolicy intent for the Incident API

## Out of scope

V4 does not add:

- a NetworkPolicy enforcement engine
- Calico
- Cilium
- production ingress
- public TLS termination
- multi-environment promotion
- blue-green or canary deployment

These are candidates for future releases.
