# Release v3.0.0 - Controlled Manual Deployment Automation

Release date: 2026-05-27

V3 adds controlled manual deployment automation to the AWS EKS Platform Golden
Path.

The goal of this release is to automate application deployment while keeping
infrastructure creation manual, auditable, and cost-aware.

## Highlights

V3 validates manual CD on top of automatic CI:

- `workflow_dispatch` deployment workflow
- GitHub Environment `dev` support
- GitHub OIDC authentication
- dedicated least-privilege AWS deploy role
- EKS access entry for the deploy role
- namespace-scoped Kubernetes RBAC
- Docker image build and push to ECR
- commit-SHA image tagging
- Helm deployment to an existing EKS cluster
- rollout validation
- in-cluster smoke test
- observability-enabled deployment mode

## Deployment model

V3 keeps CI and CD deliberately separated.

CI runs automatically on repository changes.

CD is triggered manually with:

```text
workflow_dispatch
```

The workflow deploys only to an existing EKS cluster.

It does not run:

```text
terraform apply
terraform destroy
eks create-cluster
eks delete-cluster
```

## Operator flow

The intended operator workflow is:

```text
make tf-apply
-> make kubeconfig
-> kubectl apply -f kubernetes/rbac/github-actions-deploy.yaml
-> GitHub Actions Deploy Incident API workflow
-> validation
-> cleanup
-> make tf-destroy
```

## IAM and OIDC model

V3 adds a dedicated AWS deploy role:

```text
github-actions-deploy
```

The role is assumed by GitHub Actions through OIDC.

It is separate from:

```text
github-actions-ecr-push
github-actions-terraform-plan
```

This separates workflow responsibilities and improves auditability.

## Kubernetes authorization model

Terraform manages the AWS IAM role and EKS access entry.

Kubernetes YAML manages namespace-scoped RBAC.

The EKS access entry maps the deploy role to the Kubernetes group:

```text
incident-api-deployers
```

The RoleBinding in the `incident-api` namespace grants deployment permissions
to that group.

The deploy role is not a cluster admin.

## Manual deployment workflow

The deployment workflow performs:

```text
checkout
-> assume AWS deploy role through GitHub OIDC
-> validate AWS caller identity
-> fail fast if EKS does not exist
-> login to Amazon ECR
-> build Docker image
-> push image with commit SHA tag
-> update kubeconfig
-> deploy with Helm
-> wait for rollout
-> run in-cluster smoke test
```

## Observability mode

V3 supports an explicit workflow input:

```text
enable_observability: false | true
```

When enabled, Helm loads:

```text
observability/incident-api-observability-values.yaml
```

This creates the Incident API ServiceMonitor when Prometheus Operator CRDs are
installed.

Both modes were validated:

- standard deployment without ServiceMonitor
- observability-enabled deployment with ServiceMonitor creation

## Real validation fixes

V3 exposed and fixed several realistic integration issues:

- missing GitHub Environment variable for the deploy role ARN
- OIDC trust policy missing the `environment:dev` subject
- EKS admin access entry already created by AWS
- Helm namespace creation blocked by namespace-scoped RBAC
- Deployment and Service name mismatch in post-deployment checks
- `kubectl run --rm` not suitable for GitHub Actions smoke tests
- missing `pods/log` permission for smoke test logs

These fixes are documented in:

```text
docs/deployment-v3-runbook.md
```

## Validation summary

V3 was validated with:

- successful GitHub OIDC role assumption

- successful Helm deployment
- successful Kubernetes rollout check
- successful in-cluster `/health` and `/ready` smoke test
- successful ServiceMonitor creation in observability mode
- successful Grafana Explore validation after deployment

## Security impact

V3 improves the platform security posture by:

- avoiding static AWS keys
- separating deploy, ECR push, and Terraform Plan roles
- avoiding cluster-admin permissions for the deploy workflow
- scoping Kubernetes authorization to the `incident-api` namespace
- keeping infrastructure creation outside the GitHub deploy workflow
- making deployment manual and auditable

## Out of scope

V3 does not include:

- GitHub Environment required reviewers
- custom least-privilege Terraform Plan policy
- Helm fullname override hardening
- NetworkPolicy
- alerting
- progressive delivery

These are handled in later releases.

## Interview explanation

```text
In V3, I implemented controlled manual deployment automation. CI runs
automatically, but deployment to EKS is triggered manually through GitHub
Actions. The workflow assumes a least-privilege AWS role through GitHub OIDC,
deploys only to an existing cluster, pushes a commit-tagged Docker image to
ECR, deploys with Helm, and validates the application with an in-cluster smoke
test. Kubernetes access is limited through namespace-scoped RBAC.
```
