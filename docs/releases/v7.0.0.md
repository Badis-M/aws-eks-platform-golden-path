# Release v7.0.0 - Self-Service Golden Path

Release date: 2026-06-01

V7 turns the AWS EKS Platform Golden Path into a reusable platform model.

The goal of this release is to define how a new service can be onboarded on
the platform using the same conventions validated with the Incident API.

## Highlights

V7 adds:

- new service onboarding checklist
- reusable golden path contract
- application team responsibilities
- platform team responsibilities
- service onboarding flow
- naming conventions
- deployment conventions
- observability and alerting conventions
- RBAC expectations
- release and rollback expectations
- cost-aware operating boundaries

## Onboarding checklist

V7 adds a checklist for onboarding new services:

```text
docs/onboarding/new-service-checklist.md
```

The checklist defines the minimum requirements for a service to be compatible
with the platform.

It covers:

- service metadata
- operational endpoints
- Prometheus metrics
- Docker requirements
- Kubernetes requirements
- Helm requirements
- observability requirements
- alerting requirements
- CI requirements
- deployment requirements
- RBAC requirements
- release requirements
- runbook requirements
- cost and cleanup requirements

## Self-service platform model

V7 also adds:

```text
docs/v7-self-service-golden-path.md
```

This document defines the platform as a reusable golden path instead of a
one-off application deployment.

The golden path is:

```text
code
-> tests
-> container image
-> Helm chart
-> CI validation
-> manual deployment
-> observability
-> alerting
-> rollback
-> runbook
```

## Platform contract

A service is compatible with the platform when it follows the golden path
contract.

The contract includes:

- application endpoint conventions
- Docker image conventions
- Kubernetes label conventions
- Helm values conventions
- observability conventions
- alerting conventions
- CI validation requirements
- manual deployment expectations
- rollback expectations
- operational runbook requirements

## Responsibilities

V7 separates responsibilities between application teams and the platform
team.

Application teams own:

- service source code
- tests
- Dockerfile
- runtime dependencies
- health endpoint
- readiness endpoint
- metrics endpoint
- service-specific metrics
- service-specific alerts
- service-specific runbooks

The platform team owns:

- Terraform infrastructure modules
- EKS lifecycle
- ECR repository model
- GitHub OIDC integration
- IAM role design
- Kubernetes RBAC patterns
- Helm chart conventions
- CI/CD workflow patterns
- observability stack installation
- platform documentation
- cost-aware cleanup procedures

## Required service endpoints

A service should expose:

```text
/health
/ready
/metrics
```

These endpoints make the service deployable, observable, and operable through
the platform workflows.

## Deployment expectations

A service deployment should follow the existing controlled deployment model:

```text
workflow_dispatch
-> GitHub Environment approval
-> GitHub OIDC authentication
-> image build and push
-> Helm upgrade
-> rollout status
-> smoke test
```

Deployment workflows should not create or destroy cloud infrastructure.

Infrastructure lifecycle remains explicit through Terraform.

## Observability expectations

Service charts should keep observability custom resources optional.

Default behavior:

```text
serviceMonitor.enabled=false
alerting.enabled=false
```

Observability mode can enable:

```text
serviceMonitor.enabled=true
alerting.enabled=true
```

This avoids rendering Prometheus Operator resources when the CRDs are not
installed.

## Security and operations impact

V7 improves the platform by defining reusable operating boundaries:

- services should avoid public exposure by default
- deploy workflows should use GitHub OIDC
- deployment permissions should be namespace-scoped where possible
- observability and alerting should be opt-in through Helm values
- rollback should be documented or automated
- cleanup must remain part of the platform operating model

## Current reference implementation

The Incident API remains the reference implementation.

It demonstrates:

- FastAPI service
- Docker image build
- ECR image push
- Helm deployment
- ServiceMonitor integration
- PrometheusRule alerting
- GitHub Actions deployment
- GitHub Environment approval
- namespace-scoped RBAC
- Helm rollback workflow
- operational runbook

## Out of scope

V7 does not add:

- a second production microservice
- automated service scaffolding
- reusable starter repository
- policy-as-code onboarding gates
- internal developer portal UI

These remain future platform enhancements.

## Final outcome

V7 defines the platform as a reusable self-service golden path:

```text
reference implementation
-> onboarding checklist
-> service contract
-> deployment model
-> observability model
-> alerting model
-> rollback model
-> cost-aware operating boundaries
```
